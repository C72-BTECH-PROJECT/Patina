## How to read a row
- **Status:** `DONE_CORRECTLY` / `DONE_BUT_BROKEN_OR_HACKY` / `STUBBED_OR_PARTIAL` / `MISSING` / `CODE_REVIEWED_UNTESTED` / `CLAIMED_UNVERIFIED`.
- **`DONE_CORRECTLY` needs both** a `file:line` that exists at the verified commit **and** a `tests/` reference (test, harness result or manual-smoke step). Same bar for every author.
- **`CODE_REVIEWED_UNTESTED`:** the code was read at the verified commit and a `file:line` is cited, but no test or harness result exercises it. Judged correct on reading, not proven. Each such row names, in Notes, the test that would promote it (`Promote with: ...`).
- **`CLAIMED_UNVERIFIED`:** a claim nobody has checked against code or tests (an owner-reported item, a self-report, an absence not yet looked for). No code-read is implied.
- Evidence is code read at the verified commit, not any team checklist. `Docs/archive/*` is history and is never evidence.
- `Delivered by`: the task or commit that put the behaviour in its current state. `unattributed<=32905c1` = could not be tied to one commit. `n/a: not built` = nothing to attribute.

**One-line state of the project.** A Python NLP service parses a resume and scores it against a job; a Node layer persists and explains that score from parsing, GitHub evidence (T-0014) and, once a candidate completes one, an LLM-generated assessment (built on `main`, merged in T-0023; single-step generation, no PFQS); a recruiter UI renders the stored explanation. **No score is produced through the app's UI at HEAD**: the Upload page only stores the file, Apply only inserts an `applications` row, and the sole scoring path, `POST /api/analyze`, has no reachable caller (`frontend/src/pages/candidate/Processing.jsx:175`; nothing navigates to `/candidate/processing`). PFQS planning, assessment anti-cheat (GR-1), OCR, LinkedIn/certificates, support-role fairness and OAuth are not built.

## Integration Requirement Assessment

The explainable end-to-end pipeline does not connect. At HEAD: resume upload stores a file; apply records an application; scoring happens only through a direct `POST /api/analyze` that the UI no longer reaches; one evidence source (parsing) feeds the composite; GitHub and assessment do not exist. Parsed entities seed nothing downstream: `entities.github` and LinkedIn are stored as `contact` and `project_links` and read by nothing (`backend/Controllers/analysis.controller.js:341,345`). The recruiter drill-down can show matched and missing skills and the similarity metrics for scores that exist, and nothing deeper. Per the CHECKLIST standard, the project has one partially-working module (parsing, with known quality gaps) and the score-on-apply link (5.14) and merged dashboard (5.15) still to build.
